SWI Wiki Data Gaps

What a browser-only ship evaluator needs, what the wiki backend already serves, what is missing, and where each missing piece lives in the mod files. Scope: base Star Wars Interworlds, DABC and RSP. Prepared by the X4 Ship Evaluator project.

The evaluator ranks ships per role (trader, miner, combat) and works out each ship's best loadout from the parts a player can buy. It needs ship physics, slots and wares, part stats and wares, thrusters, cargo and hangar sizes, and faction names.

Almost all of this is already in the wiki's JSON, as the raw game macros. The gaps below are small and come from files the mods already ship, except thrusters, which come from the base game.

How the ship pages work out cargo and hangars

Neither swi-api nor the static JSON holds a storage capacity. A ship record only names the storage macros it connects, for example the E-wing's storage_container_550_macro and shipstorage_gen_xs_01_macro.

Each ship page loads that record (swi-api for base ships, /submods/<mod>/ships/…json for submods). Two functions in the page's own script then read the numbers out of the names:

  • parseShipStorage handles cargo: storage_<type>_<volume>, with universal split into container, solid and liquid.
  • parseHangers handles the S and M hangars: shipstorage_…_<s|m>_cap<n>.

That works whenever a name states the true size, which is most of the time. The failures come from four causes.

Four causes

  1. The "Gozanti C-ROC Raider fix" hits the wrong ships. Every version of the script turns any container 5000 storage into 10,000 universal cargo. Five ships really do carry 5,000 container cargo and now show the wrong value. The Raider itself is missed: its storage is storage_universal_5000_macro, which really holds 10,000, so the page still shows 5,000.
  2. Names that don't state the size. shipstorage_gen_s_01_macro (40 S), shipstorage_gen_m_01_macro (10 M) and shipstorage_gen_s_four_macro (4 S) have no cap<n>. The submod pages know only the first of these (a knownHangars entry); the base pages know none of them.
  3. Values are overwritten, not added up. Both functions assign (result[key] = value), so a ship with several storages of one kind shows only the last one. The DABC Providence Dreadnaught has three shipstorage_gen_s_01 (3 × 40) and shows 40. No ship has two cargo storages today, but the cargo function has the same flaw.
  4. Three copies of the script. Each Wiki.js page carries its own copy, and they have drifted apart:

Method (2026-10-17): we ran each of the 292 ship pages of base SWI, DABC and RSP with its own copy of the two functions on its own ship record, exactly as the page does. We compared the result with the cargo @max and dock @capacity of the same macros in the SWI 0.9.1, DABC and RSP files, summed per ship. Only S and M hangars are shown on the pages, so only those were compared.

The lasting fix is the one in the table above: resolve the storage macros when the JSON is generated (or publish a storage.json). Then the pages can show cargo @max and dock @capacity directly, and the name parsing, the C-ROC exception and the hand-made hangar table can all go. Until then, one shared script file for all ship pages would at least stop the copies drifting apart.

Smaller issues found while reading the data

  • Unmatched base part wares. 22 base parts don't match a ware by component @ref. Most are Xenon or legacy parts, but a few are filed under the wrong ware group: weapon_sw4_s_laser sits in group turrets and turret_s_cec_twin in weapons.
  • Unresolved names in base wares. ware._name and identification._name in the base API still hold {page,id} references, which the submod JSON resolves to text.
  • No slot _group on base ships. Submod ship files have it; the base API records don't.
  • Empty component entries. About 15% of components entries are {} (dock-only matches). Harmless, but every reader has to skip them.
  • XS list. swi-api.siifr.net/ships/xs/list/full answers HTTP 500 (a missing boarding-pod XML file).
  • Wiki page mix-up. The page /en/ships/xl loads the DABC XL list instead of the base one.

Not gaps

  • Missing physics.accfactors (all DABC ships, half of the base ships): the game treats a missing factor as 1.0. We confirmed this against the game's own figures.
  • All values are strings in the JSON. That's fine; readers parse them.

Movement formulas, checked against the game

The wiki's notes list several movement formulas as candidates checked on the Bellator only. We measured them with an in-game probe that calls the shipyard's own statistics function (GetLoadoutStatistics5) on 2040 ship, engine and thruster combinations (X4 8.00 + SWI). Every formula below matched with 0.00% scatter.

Two values the game does not report, so they stay unverified: yaw acceleration (thrust.yaw ÷ inertia.yaw) and travel deceleration (travel speed ÷ travel.release).

Weapon DPS is only approximate from the files. Damage per shot × projectiles × shots per second (with magazines: shots ÷ (shots ÷ rate + reload)) is about 1.66 times too low for weapons and about 2.2 times too high for turrets, averaged over 470 parts the game measured. Treat computed DPS columns as estimates.

Reading the data from another site

Browsers only let a page read data from another host when that host allows it (CORS). Today:

  • swi-api.siifr.net allows only https://swi.siifr.net.
  • The static JSON on swi.siifr.net sends no CORS header, so only pages on swi.siifr.net itself can read it.

So a page embedded on the wiki can read everything. A copy hosted elsewhere, for example on GitHub Pages, can't read anything until both hosts allow that origin: an origin added to swi-api's cors() options, and an Access-Control-Allow-Origin rule for the static JSON in Wiki.js or Cloudflare.

Our proposal: embed the evaluator on the wiki, as offered. Until the gaps above are filled on your side, it loads a small supplement file (thrusters, storage, wares, factions) from our GitHub Pages, which any site may read. Each gap you close removes that part of the supplement.

One note on SiifrWikiSubmodTool.ps1

We read the generator script, without a token. It looks careful: XML is parsed with DTDs ignored and no external resolution, the token is never stored, and uploads ask before they run.

One risk is worth a guard. Convert mod folder deletes <destination>\<mod> recursively when it exists and the user answers Y. If the extracted mod folder is itself named after the mod and the user picks its parent as the destination, the source is deleted before it is copied. A check that refuses a destination equal to, inside or containing the source would close that.
